## 3. API-First Guardrail (New Hard Rule)
From this batch forward, API-first is mandatory for both Sail Southern and Sailing Almanac.

### Principles:
* Every new feature defines its API contract before UI implementation.
* All external APIs live under `/api/v1/...` (versioned).
* We maintain a single OpenAPI spec file in the monorepo and keep it in sync with the implementation.
* No ad hoc endpoints: every route must be documented and categorized as:
  - Public
  - Partner
  - Internal
  - Admin

### Technical Requirements:
* **Base path:** `/api/v1`
* **Pagination:** cursor-based for all large collections
* **Errors:** consistent envelope (e.g., `{ error: { code, message, details? } }`)
* **Metadata:** where applicable, include provenance and rights flags (especially for source-derived records)
* **Security:** API keys or token auth for anything beyond public reads; rate limiting in front of public API

### AG Integration Scope:
1. Introduce an OpenAPI contract (JSON or YAML) in the repo.
2. Wire the existing/planned endpoints into `/api/v1`.
3. Update or create middleware leveraging `@stax/api-middleware` for validation and error handling.

## 9. Next-Batch Workstream: Outbound Social Archive + Dashboard (New Workstream)

We have officially added the **Outbound Social Archive + Dashboard** subsystem to the Sailing Almanac / Sail Southern roadmap. This treats every published social post as part of the project's historical record (establishing a "Library of Congress for sailing" posture).

### Required Principles:
1. **Archive at Creation/Publish Time**: Capture details automatically when posting, not retroactively.
2. **Mandatory Archive Write on Publish**: Any outbound social publish path (Mastodon, Nostr, AT Protocol/Bluesky, or any future service) *must* execute an archive write as a non-optional step in the publishing pipeline. This includes writing a canonical `social_posts` record, links, media, and `social_post_delivery` metadata per target platform.
3. **Structured DB First**: Postgres and object storage constitute the canonical system of record.
4. **No Airtable-First Dependency**: Airtable may be utilized as a downstream operator cockpit/review workspace, but the database is the source of truth.
5. **API-First & Dashboard Isolation**: The internal dashboard and admin UI must act as a consumer of the versioned `/api/v1` archive APIs and defined service functions. Dashboard code is strictly isolated from executing ad-hoc raw SQL queries against the archive schemas directly.
6. **Multi-Rail Distribution Integration**: The multi-rail micro-newsletter / social distribution layer (Mastodon + Nostr + Bluesky) must hook directly into the archive. Each outbound platform post is linked back to its canonical internal content object (newsletter/micro-edition/outbound package), and platform delivery records are attached as child records of that parent canonical object. Platform adapters remain thin translation layers.

### Scope of Deliverables:
* **Data Model**: Design and apply migrations for tables: `social_accounts`, `social_posts`, `social_post_media`, `social_post_metrics_snapshots`, `social_post_archives`, `social_post_revisions`, `social_post_links`, and `social_post_captures`.
* **Archival Capture**: At publication time, trigger background worker captures (DB record, screenshot/HTML reference, and external Wayback SPN trigger).
* **Metrics Snapshots**: Schedule periodic background jobs to fetch engagement snapshots (likes, shares, replies, impressions) over time, storing time-series records without overwriting historical data.
* **Internal Dashboard**: Build a dashboard layer that consumes versioned `/api/v1` routes, presenting outbound posts, performance metrics, edit/deletion alerts, and curator action flags.
